## Main Failure Types

### 1. SQL semantic errors are the real bottleneck

Examples:

```text
club_leader:
needs member -> club_leader -> club join, but model used club.Team_Leader

musical:
gold counts actors that appear in musicals, model used LEFT JOIN and included musicals with zero actors

university_rank:
question asks conferences with avg enrollment > 2000, model computed AVG over universities where enrollment > 2000

region_building:
question asks top five by area, model ordered ascending instead of DESC
```

Implication:

```text
Need more hard SFT data around grouping semantics, join-path selection, EXCEPT/INTERSECT, ORDER BY direction, and projection discipline.
```

### 2. Literal grounding and translated entity names still hurt

Examples:

```text
movie_2:
gold uses theater names 'Odeon' and 'Imperial', model searched 'Odeon Cinema' and 'Empire Cinema'

culture_company:
gold filters incorporated_in = "中国", model repeatedly searched company_name = "China"

sing_contest:
model confused original_artist value semantics and joined through participants
```

Implication:

```text
Hard validation and future teacher rollouts should prefer English questions where possible, or require preview_rows when literals/entities are uncertain.
Chinese translated literals should be audited aggressively.
```

### 3. The model sometimes executes a good SQL but does not finalize

Examples:

```text
course_teach:
model executed SELECT Hometown FROM teacher GROUP BY Hometown HAVING COUNT(*) >= 2, then kept probing until budget exceeded

candidate_poll:
model executed SELECT * FROM people, then failed to emit final

race_track:
model executed the apparent gold-equivalent join, then parse_failed instead of final
```

Implication:

```text
Need targeted finalization-after-success examples:
observation ok + result enough -> final with exactly the last successful SQL.
This can be built without teacher.
```

### 4. Some "wrong_result" rows are projection/strictness issues

Examples:

```text
document_management:
question asks count in each role; model outputs role_code then count, while gold outputs count then role_code

soccer_3:
question asks countries; model outputs country plus count

election_representative:
question asks lifespans; model outputs full representative columns
```

Implication:

```text
The main metric should stay execution-value based, but hard eval should track projection-overselect separately.
Training should include "return only requested columns" examples.
```

## Training Data Consequences

Do not keep training blindly on the same 5.5k SFT set. The next dataset patch should add:

```text
1. Hard SQL traces:
   JOIN path, nested/EXCEPT/INTERSECT, GROUP BY/HAVING, ORDER BY direction.

2. Literal-grounding traces:
   Use preview_rows when entity values or translated names are uncertain.

3. Finalization anchors:
   If execute_sql succeeded and result answers the question, final immediately.

4. Projection-discipline SQL core:
   Output only the requested columns, not explanatory extras.

5. Real repair transitions:
   no such column/table, wrong join path, repeated SQL after error.
```

## DeepSeek Teacher Audit

DeepSeek V4 Pro should not be blindly trusted on hard SQLite tasks. The right local audit is:

```text
hard task pool
-> teacher rollout
-> execute verifier
-> keep only pass / repairable cases
-> categorize teacher failures
```

This can run locally because it only needs API calls and SQLite execution, not a GPU. GPU is only needed for student model rollout/training.
