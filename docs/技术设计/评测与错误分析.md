# 评测与错误分析

## 当前指标口径

| 指标 | 含义 |
|---|---|
| `strict_pass` | 列名和完整值均一致 |
| `equivalent_output` | 列数和完整值一致，允许 alias 不同 |
| `pred_executable` | final SQL 可执行 |
| `submitted` | 在预算内输出 final |
| `canonical_protocol_valid` | 输出符合唯一 JSON schema |
| `parse_failed` | 无法解析 action/final |
| `budget_exceeded` | 工具步数耗尽仍未完成 |
| `final_matches_last_execute` | final 与最后成功执行 SQL 一致 |

结果文件见 [`results/`](../../results/README.md)。当前仓库保留的是结构化摘要，而不是逐条 SFT/RL 原始 rollout；因此可以复核指标定义、数值、run 身份和训练配置，但不能从仓库独立重算每个历史聚合值。

## 历史 Mini-Dev 错误样本

下列分析来自旧版 V2 checkpoint-686/continued-250 的 60-task mini-dev 产物，原始路径现已不在仓库中。因此它是历史定性材料，不代表当前 checkpoint-600 或 RL 模型的最新错误比例。

当时的主要错误类型为：

1. SQL 语义：join 路径、聚合粒度、`HAVING`、集合操作和排序方向；
2. literal grounding：实体翻译、枚举值和文本大小写；
3. finalization：执行了可用 SQL，却继续探索直至超步数或解析失败；
4. projection：返回多余列、列顺序不同或没有只输出问题要求的字段。

这些结论仍能指导数据设计：增加复杂 SQL 轨迹；literal 不确定时使用 `preview_rows`；加入“成功后立即 final”的锚点；单独训练 projection discipline；优先保留来自真实 SQLite observation 的 repair transition。

## 如何产生同步的错误报告

若要把本文件升级为当前模型的定量报告，应保存并提交或发布：

1. 固定任务文件及哈希；
2. checkpoint、基座、协议、温度、最大步数；
3. 逐任务 rollout JSONL；
4. 聚合 summary JSON；
5. 按错误类别生成的审计表。

在缺少逐条原始 rollout 时，不应给历史案例重新贴上“当前结果”的标签。
